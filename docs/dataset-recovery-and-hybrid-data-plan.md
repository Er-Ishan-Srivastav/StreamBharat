# StreamBharat — Dataset Recovery and Hybrid Data Plan

**Status:** Planning baseline  
**Branch:** `feature/hybrid-dataset-factory`  
**Decision:** Attempt recovery of the original course dataset first; build a reproducible synthetic OTT source dataset; use public data only for the domains it genuinely covers.

## 1. Objective

Make the StreamBharat project reproducible when the separately distributed course dataset is unavailable, without claiming generated data is the original course data or that public ratings are OTT playback telemetry.

The repository currently documents two separate assets:

- The original course dataset specification in `docs/source-materials/StreamBharat-Dataset-README.md`.
- A small deterministic Kafka integration generator in `scripts/generate_demo_data.py`.

Keep the existing small generator for the acceptance/demo path. The full dataset factory described here is a separate deliverable and must not silently change the existing demo's behaviour.

## 2. Data provenance contract

Every source file used in a run must be classified as exactly one of:

| Class | Meaning | Permitted use |
|---|---|---|
| `course_original` | Supplied course dataset, obtained from the course distribution | Run the original Q1–Q20 workload |
| `public_external` | Public third-party dataset, with source URL, version, retrieval date and applicable terms | Use only for fields and analyses actually represented by that source |
| `synthetic_generated` | Generated by StreamBharat's factory with a recorded seed and configuration | Exercise OTT event, billing, ads, CDN and operational pipelines |
| `synthetic_derived` | Generated records derived from public inputs using explicit rules | Controlled integration/enrichment experiments; never label as observed real-world behaviour |

Do not merge provenance classes without retaining a row-level or dataset-level source marker. Do not describe synthetic playback, payment, advertising or CDN events as real customer activity.

## 3. Recovery workstream — original course dataset

The course dataset README says the files are distributed separately and describes approximately 590 MB uncompressed. It specifies 2,500 accounts, 4,736 profiles, 389 titles / 740 episodes, 1,621,902 playback events and supporting billing, search, ads, CDN and reference data.

Recovery checklist:

1. Check the course LMS / classroom project resources for the Project 4 dataset attachment or download link.
2. Search local Downloads, Documents, Desktop, course-workspace folders, external drives and archive folders for names containing `StreamBharat`, `dataset`, `Project-4`, `ott`, `.zip`, `.7z` or `.tar`.
3. Check the original course email / class group / shared drive for the instructor's dataset-distribution message.
4. Ask the project teammates whether anyone retained the original archive; obtain the original archive rather than a teammate's edited working copy.
5. If found, preserve the archive unchanged, calculate SHA-256, extract to a local directory and run the repository preflight against a copy.
6. Compare the extracted inventory and row counts with the repository dataset specification before running any pipeline.

**Do not commit the archive or extracted course data to Git.** Keep it local under `data/raw/` (or another explicitly selected external data root) and keep credentials and private course links out of issue comments and commits.

If the original archive cannot be recovered, record that as a project limitation and continue with the synthetic/hybrid track below.

## 4. Public-data enrichment

### Selected source: MovieLens 32M

Official source: https://grouplens.org/datasets/movielens/32m/

The stable MovieLens 32M release contains 32,000,204 ratings and 2,000,072 tag applications across 87,585 movies from 200,948 anonymised users. It includes `ratings.csv`, `movies.csv`, `tags.csv` and `links.csv`.

Potential StreamBharat use:

- Movie catalogue metadata and genre enrichment from `movies.csv`.
- Explicit user-item rating signals for recommendation experiments from `ratings.csv`.
- User-generated tags for content discovery experiments from `tags.csv`.
- External identifiers from `links.csv` for optional metadata joins.

Important limitations:

- MovieLens is a movie-rating/recommendation dataset, not an OTT service event log.
- It does not provide playback starts, heartbeats, pauses, watch completion, subscription lifecycle, payments, ad impressions, CDN requests, regional licences or OTT customer demographics.
- Do not fabricate playback sessions by relabelling ratings.
- MovieLens timestamps and user identifiers retain their source meaning; document any derived features separately.
- Review the upstream README and terms before use. Acknowledge GroupLens as required. Do not assume commercial use or unrestricted redistribution is permitted. Do not place the raw archive in this repository.

Use the stable 32M release for reproducible research, not the changing `latest` release. Start with a small sample for development and only process the full archive when the local environment has sufficient storage and compute.

## 5. Synthetic OTT source generation

Create a new `data_factory/` package. It must not replace `scripts/generate_demo_data.py`.

### Required source domains

| Domain | Required synthetic assets | Main use |
|---|---|---|
| App identity | users, profiles | Joins, cohorts, kids-profile rules |
| Content | monthly catalogue snapshots, episodes, licences | Catalogue, history, regional availability |
| Playback | server-arrival-day JSONL events | Sessions, watch time, completion, late events |
| Billing | subscription events, gateway settlements | Lifecycle, MRR, reconciliation |
| Discovery | search logs, ratings | Search funnel, recommendation features |
| Advertising | campaigns, breaks, impressions | Fill rate, delivery, pacing, frequency caps |
| CDN | AkashCDN raw logs, NimbusEdge TSV logs | Parsing, regional egress and cost |
| Reference | plans, partners, genre mapping, city/state, CDN edges/rates, published metrics | Enrichment and reconciliation |

The factory should match the documented source schemas and directory layout wherever the course specification provides them. It should generate all files required by `scripts/preflight_dataset.py` before claiming compatibility with the original course-data pipeline.

### Generation profiles

- `development`: small, quick, deterministic data for unit tests and notebook iteration.
- `acceptance`: bounded but relationally complete data that exercises all supported source contracts and known data-quality cases.
- `full`: approximately the scale of the documented course sample, subject to local storage and runtime.

Configuration must include a fixed random seed, date range, entity counts, event-volume controls and defect rates. A run must emit a manifest containing generator version, seed, config hash, generation timestamp, file paths, formats, row counts, byte sizes and SHA-256 checksums.

### Data realism and integrity

- Generate stable primary keys and valid foreign-key relationships.
- Generate coherent lifecycle sequences (for example, subscription before renewal/cancellation).
- Generate playback event sequences with plausible positions and event-time/server-arrival-time differences.
- Generate valid and intentionally invalid records using configurable defect rates.
- Include duplicate IDs, malformed/null fields, invalid enums, client-clock skew, delayed offline uploads, unmatched impressions, payment failures and CDN status/size anomalies.
- Make defects deterministic for a fixed seed and record the injected defect counts in the manifest.
- Avoid using real personal information. Use fictional names/identifiers and clearly synthetic locations or anonymised city-level categories.

## 7. Pipeline and evidence plan

For every implemented source domain, capture:

1. **Source evidence:** schema, representative input rows and source provenance.
2. **Bronze evidence:** source row count, ingestion count, source identity and ingestion metadata.
3. **Silver evidence:** accepted/rejected counts, duplicate handling, null/enum checks, timestamp rules and output schema.
4. **Gold evidence:** business metric definitions, output counts and reconciliation checks.
5. **Serving evidence:** PostgreSQL table/view row counts and reproducible SQL.
6. **BI evidence:** dashboard screenshots/export and the exact query/view behind each metric.

A transformation evidence record should include run ID, input manifest/checksum, code revision, configuration, output location, row counts, rejected/quarantined counts and validation result.

Do not use screenshots alone as proof. Retain machine-readable validation JSON and SQL/query definitions.

## 8. Acceptance gates

### Gate A — source inventory
- Original dataset recovery attempt documented.
- MovieLens terms reviewed and source metadata recorded if downloaded.
- No raw or generated data committed to Git.

### Gate B — factory integrity
- Same seed and config produce stable identifiers and equivalent data outputs.
- All declared foreign keys resolve.
- All expected source schemas validate.
- Manifest checksums and row counts match actual files.
- Injected defects match configured rates within deterministic rules.

### Gate C — pipeline compatibility
- Synthetic dataset passes a dedicated synthetic preflight.
- Course-data preflight compatibility is claimed only if every required file and schema is actually present.
- Each supported transformation completes and has before/after evidence.
- Bronze-to-Silver and Silver-to-Gold reconciliation totals balance, including quarantined rows.

### Gate D — business outputs
- Metric definitions are documented.
- Financial and advertising reconciliations pass their explicit rules.
- Recommendation experiments identify whether the interaction source is MovieLens ratings or synthetic OTT events.
- Dashboards label the data mode clearly: Original Course, Public MovieLens, or Synthetic.

## 9. Immediate implementation sequence

1. Add a dedicated synthetic-data preflight rather than weakening the original course preflight.
2. Add the factory config and manifest contract.
3. Implement identity, profile and catalogue generators with referential-integrity tests.
4. Implement playback event generation and quality-defect injection.
5. Implement billing, discovery, advertising, CDN and reference generators.
6. Validate the generated file inventory against the documented course schemas.
7. Add MovieLens ingestion as a separate public-data adapter and retain its source identifiers.
8. Run the existing transformation modules against the synthetic data only where their input contracts match; record unsupported or incomplete modules instead of claiming full Q1–Q20 completion.
9. Produce Bronze/Silver/Gold reconciliation reports and dashboard data-mode labels.

## 10. Reporting language

Use:

- "Synthetic OTT events generated by the StreamBharat Dataset Factory."
- "MovieLens public ratings used for a separate recommendation experiment."
- "Original course dataset not yet recovered / not used in this run."
- "Pipeline transformation demonstrated on reproducible synthetic inputs."

Do not use:

- "Real OTT user behaviour" for generated records.
- "Original course dataset processed" when using generated or public data.
- "Production performance" based only on a small local synthetic run.
